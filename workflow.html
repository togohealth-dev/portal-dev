How a project
gets to production

Every feature runs the same trail — from a rough idea to real clinicians using it. Like a good sled team: steady, in order, nobody skips ahead.

New here? Read this once, top to bottom. It's the whole process — who does what, where the loops are, and which rules never bend.

⚠ Production DB · real patients
The one thing to burn into your memory: only localhost uses the sandbox. Alpha, beta and gamma all read and write the same real production database — on different versions of the code, at the same time. That's why schema changes are additive-only, and why test patients never go anywhere but your own machine.
Phase 1 · Idea → Draft

Claude

A project gets written 📝

Ideas arrive from anywhere — a provider's complaint, a nurse's shortcut, a certification gap, Scott's roadmap. Claude turns each one into a real project on the tracker, written to the standards in our instruction files, so the scope, gotchas and constraints are captured before anyone codes.

It lands in Drafts or Future Ideas with a priority of 1–5.

Always open: users can drop a new idea in at any time — it becomes a draft or future idea and joins the queue. Nothing is ever "too late" to suggest.

Phase 2 · Build on localhost
3
Developer

Project Tracker: Copy Prompt / Claude: Open a NEW Session 🤖

Hit Copy Prompt on the project card. That gives you the project tracker's prompt — this project's build brief plus every standing instruction that applies to all our work: PR size, schema safety, where secrets live, auth rules, which certification criteria it touches.

The prompt doesn't try to contain everything. It points Claude at our instruction files — the .md files in the repo and strategy docs — which hold the deeper detail. Claude reads those itself at the start of the session, so you don't have to memorise any of it.

Paste the whole thing into a fresh Claude session.

One session = one project = one branch. Don't build two projects in one session; they'll tangle.

Copy Promptnew session
4
Developer + Claude

Build, committing as you go 💾

Work in small commits on a feature branch. Commits are your undo button and your handoff notes — a project with one giant commit at the end is very hard for anyone else to pick up.

🤝
Handoff loop: a project can move to another developer mid-build. Because the work lives in commits on a branch (not in one person's chat window), they pick up where you stopped.
5
Developer

See it on localhost 👀

Run it on your own machine, pointed at the sandbox database — fake patients, safe to break. Sign in the normal way: password first, then your passkey for MFA.

If your localhost is calling the production backend, stop — that's real patient data, and it's the one setup mistake that actually matters.

sandbox · localhost:5434
6
Developer + Claude

Get the code reviewed by a second model 🔍

  • In the session, run /code-review on your working diff.
  • Pick the reviewer by complexity: Fable for small, contained changes — copy, styling, a single component. Opus 5 for anything touching the database schema, auth, orders, or clinical logic.
  • Use a different model than the one that wrote the code. A model reviewing its own work misses its own blind spots.
  • Fix what it flags, then re-run the review until it comes back clean.
  • If a finding looks wrong, say so — don't just apply it. Reviews are suggestions, not orders.
7
Developer + Claude

Have Claude give you a list of new features to test 📋

  • Ask Claude: "list every new feature and screen in this project that I should test" — now you have a checklist instead of guessing.
  • Walk that list on localhost yourself. For each item, try the normal path, the empty state, and one wrong input.
  • Use it the way a nurse or provider would, not the way you built it.
  • A clean build and passing type-checks are not testing. Only clicking is.
🔁
Iterate here, not later: fix → reload → click again, as many rounds as it takes. Bugs are cheap on localhost and expensive once real users meet them.

Open the PR, Mark it Alpha Ready 🚀

Claude pushes the branch and opens a pull request, then moves the card to PR Alpha Ready and tags Scott. Keep PRs small — 1–2 features. If a build starts sprawling, split it into another project rather than growing the PR.

That label does one more thing: it starts advancing the ONC/MIPS certification bars automatically.

🚫

Code review 🧐

Scott reads the diff before anything touches real data — schema safety, auth, and whether old and new code can live together in the shared database.

↩️
Revision loop: if something's off, the card goes to Needs Revision and comes straight back to you. Normal, not a failure.

Scott deploys the feature pointed at the production database. Simple changes ride the shared alpha environment; a complex one gets its own alpha page so nothing else muddies the test.

The card moves to Alpha Testing with a link straight to the build.

10
QA leads · Greg, Morgan, Jordan

QA tests it for real 🧪

The clinical leads use the feature against real charts — the first time it meets messy, real-world data instead of tidy sandbox rows.

↩️
Two ways out: send it back for revision (→ back to Phase 2 with notes), or mark it Ready for Beta and let it into the next combined build.

Phase 5 · Beta — everything together
Scott

Combined into a beta build 🧩

Every two weeks Scott merges the cycle's alphas into one beta and ships it to the beta group — MAs, nurses, staff and providers. This is the first time the changes run together, which is where surprises actually live.

📧
"What's new" email goes out to beta users, in plain language, so they know what changed and what to look at.

11
Beta users → Scott

Real people, real feedback 🗣️

Beta users work normally and report what's confusing or broken. Scott fixes bugs and glitches directly.

🌱
Feedback becomes work: a small fix is patched in beta; a bigger request becomes a brand-new project back at Phase 1.
🧯
Emergency valve: Scott can switch a feature back off in beta if it's causing harm. Shipping is reversible — that's the point of having stages.

When beta holds up, Scott promotes it to gamma — every user, every facility. Same two-week rhythm: this cycle's alphas become the new beta while the last beta becomes gamma.

📧
"What's new in version x.y.z" goes to all users — the release note that closes the loop for the people who asked for it.

Everyone

The trail loops back 🔄

Production isn't the end. Bugs, glitches and "could it also…" all flow back in as feedback, and become the next drafts and future ideas.

Rules that never bend

Most of the process is flexible. These aren't — each one exists because breaking it once caused real damage or would put patient data at risk.

🗄️ The database is shared

Alpha, beta and gamma all use the same production database on different code versions, simultaneously. Schema changes are additive only — new columns nullable or defaulted. Never rename, retype, or repurpose a column old code still reads.

🧪 Test data stays home

Test patients and PHI live on your local sandbox only. A row you create for testing is visible in production the moment it exists — you cannot "seed just alpha."

✂️ Small PRs

1–2 features per PR. If a build grows a third, stop and split it into a new project. Big PRs sit unreviewed and break in ways nobody can untangle.

🛤️ One lane at a time

One session, one project, one branch, one worktree — and the worktree lives in ~/claude/togo/togo-emr/wt/, never loose in your home folder. Mixing two projects in one session is the fastest way to an unreviewable diff.

📁 Four folders, four lanes

~/claude/togo/togo-emr is the EMR. ~/claude/togo/togo-facility-tools is anything that reaches out to a facility's own systems (PointClickCare). ~/claude/personal is your machine setup and side projects. ~/claude/sege exists only if you were granted access. Each carries its own CLAUDE.md, so a session loads the right rules from where it was opened — and home is not a lane. Never write one lane's files into another's tree.

🔑 Secrets have one home

Every credential lives in the gitignored portal/backend/.env (Secret Manager once deployed). Missing a key? Ask Greg or Scott. Never invent one, never hardcode it, never paste one into an issue, PR or chat.

🔐 Auth is MFA

Anything touching sign-in, identity, sessions or tokens gets built on our MFA path — password first, then a passkey. Legacy auth code is being retired, so don't extend it. If a change looks like it needs the old path, stop and flag it.

🩺 Compiling isn't testing

A green build proves nothing about whether a nurse can use the screen. Click every new path yourself before opening the PR.

🤖 AI on patient data

PHI-touching AI runs server-side only, through the provider we hold a BAA with, sending the minimum necessary. A clinician confirms every write, and the decision gets logged.

📈 Certification updates itself

Each project owns a slice of the ONC/MIPS criteria it advances, and the bars fill from the card's status label — alpha 50% · beta 75% · gamma 100%. Label the card correctly and the number takes care of itself. Never hand-edit a percentage.

⏱️ The two-week rhythm

Every other Tuesday, both promotions happen at once: this cycle's alphas become the new beta, and the previous beta becomes gamma.

⚡ The fast-track exception

Genuinely low-risk changes — copy tweaks, small UI, config — can go straight to gamma at Scott's or Greg's call. Never for schema, auth, patient data, or clinical logic.

🗑️ Stopping is allowed

Projects that turn out to be wrong get marked Abandoned with the reason written down. A documented dead end is worth more than a half-built feature nobody trusts.
